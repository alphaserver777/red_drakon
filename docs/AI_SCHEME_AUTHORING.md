# Инструкция для ИИ: создание исполнимых схем DRAKON

## Главный принцип

Схема — единая точка правды для оператора, ИИ и воркёра. Оператор читает и
правит блоки, ИИ строит и проверяет их, воркёр проходит их в том же порядке.
ИИ не заменяет схему свободным рассуждением, не пропускает блоки и не выполняет
действие, которого нет в утверждённой версии.

## Роли

| Роль | Обязанность |
|---|---|
| Оператор | Задаёт цель, границу, допускает запуск и утверждает версию. |
| ИИ-составитель | Предлагает, создаёт и проверяет схему. |
| ИИ-исполнитель | Получает текущий блок, выполняет разрешённое действие и возвращает результат. |
| Исполнитель | Проверяет версию, ведёт хешированный журнал, запрещает пропуск блоков и лишние команды. |

Составление и исполнение — разные режимы. Во время исполнения нельзя изменять
утверждённую схему.

## До создания схемы

ИИ сначала обязан показать оператору:

1. Название этапа и единственный измеримый результат.
2. Входные данные из предыдущей схемы.
3. Результаты, передаваемые следующей схеме или API.
4. Условия остановки.
5. Разрешённые и запрещённые методы.

Не дублировать в каждой схеме общую границу, VPN, номер задачи и запреты, если
они уже установлены предыдущими этапами и передаются в контексте запуска.

## Декомпозиция

Одна схема отвечает на один законченный вопрос. Для процесса внутренней
разведки это: выбор задачи → VPN → живые хосты → без учётных данных → API и
завершение.

Создавать новый силуэт, если меняются входные данные, результат, набор
протоколов или часть перестаёт читаться на одном экране. Не делать новую схему
ради одного простого действия.

Успешный выход ведёт переходом в следующую схему. `blocked`, `error`,
`empty` и прочие нештатные результаты ведут в обычный `Конец`.

## Правила DRAKON

1. Штатный путь идёт сверху вниз по левой вертикали.
2. Вопрос всегда допускает ответы «Да» и «Нет».
3. «Да» продолжает ожидаемый путь; «Нет», ошибки и блокировки уходят вправо.
4. Один блок содержит одно действие или одну проверку.
5. Действие начинается с глагола: «Получить…», «Проверить…», «Сохранить…».
6. Вопрос описывает наблюдаемый факт: «Есть живые хосты?».
7. У каждой ветви есть явный итог: переход, `live`, `empty`, `blocked`,
   `error` или `Конец`.
8. Нельзя оставлять висячие ветви, пересечения линий и безымянные выходы.
9. Номера блоков назначает редактор; их не меняют вручную.
10. Переход к другой схеме создаётся только блоком «Вставка» с назначенной
    целевой схемой. Обычный блок действия не является переходом.

## Текст блока

Использовать форму: `действие + объект + ограничение + результат`.

Примеры:

- «Определить доступные SMB-сервисы среди живых хостов; сохранить факт и
  доказательство».
- «Проверить анонимный LDAP только на обнаруженных контроллерах домена».
- «Сохранить coverage обработанных хостов и перейти к записи через API».

Не хранить в блоке секреты, токены, пароли, полный вывод команды и несколько
несвязанных действий. Команда может быть названа для однозначности, но её
параметры и защита задаются исполнителем.

## Этап без учётных данных

Схема `04-нет-учётных-данных` строится из следующих частей, без повторной
проверки общей границы:

1. Получить живые хосты и уже обнаруженные сервисы.
2. Отобрать применимые утверждённые шаблоны MITRE по подтверждённому протоколу.
3. Отдельными ветвями выполнить разрешённые проверки SMB, LDAP/Kerberos, DNS,
   RDP, WinRM, SSH, MSSQL, SNMP, веб и NAS — только при наличии сервиса.
4. После каждой проверки ответить: есть ли подтверждённый факт или минимальный
   доступ без учётных данных?
5. При положительном результате сохранить сервис, факт, технику MITRE и
   доказательство.
6. При отсутствии факта сохранить coverage: что проверено, где и почему факт
   отсутствует или проверка неприменима.
7. После обработки всех кандидатов перейти к записи через API.

Подбор паролей, использование учётных данных, эксплуатация уязвимостей и
движение по сети являются отдельными этапами. Их нельзя добавлять в этот
силуэт под видом проверки без учётных данных.

## Связь с исполнителем

Схема полностью описывает смысл процесса. Исполняемый контракт не создаёт
вторую схему, а содержит только техническую привязку: номер блока,
разрешённый обработчик, тип входа и результата, имя доказательства и допустимые
следующие блоки.

Для каждого исполнимого блока существует ровно один обработчик, и для каждого
обработчика — блок в утверждённой схеме. Сборка отклоняет версию при нарушении
любого из этих правил.

Исполнитель выдаёт ИИ только текущий блок. ИИ не выбирает произвольную
команду, не перескакивает через вопрос и не продолжает работу после
контрольной точки, `blocked` или `error`.

## Доказательства и API

Каждое действие заканчивается одним из результатов:

- подтверждённый факт и имя файла доказательства;
- отсутствие факта с coverage;
- неприменимость с причиной;
- блокировка или ошибка с причиной.

Сначала исполнитель записывает событие в локальный журнал с хеш-цепочкой,
затем передаёт безопасную проекцию в панель. При недоступности панели действие
не повторяется: событие остаётся в очереди. В API не передаются секреты,
команды с секретами и содержимое доказательств.

## Проверка перед утверждением

ИИ обязан проверить и показать оператору:

- один вход и достижимость всех блоков;
- ветви «Да» и «Нет» у каждого вопроса;
- явный итог каждой ветви;
- отсутствие запрещённых действий и неявных переходов;
- ограниченный список кандидатов у каждого сетевого действия;
- доказательство или coverage для каждого результата;
- покрытие всех исполнимых блоков контрактом;
- сухой прогон штатного пути, `empty`, `blocked` и `error`;
- читаемость силуэта в редакторе.

После проверки оператор экспортирует набор, вручную создаёт Git-коммит и тег.
Только тег, указывающий на точный SHA коммита, является утверждённой версией.
Черновик в веб-редакторе никогда не разрешает реальный запуск.

## Шаблон задания ИИ

```text
Составь или измени схему DRAKON для этапа <название>.
Входы: <перечень>.
Единственный результат: <результат>.
Разрешённые методы: <перечень>.
Запрещённые методы: <перечень>.
Следующая схема при успехе: <название>.

Построй читаемый силуэт. Не повторяй общие проверки предыдущих этапов.
Для каждого действия укажи доказательство или coverage. Не добавляй команд,
которых нет среди утверждённых шаблонов. Сначала покажи план; не выпускай тег
и не запускай воркер без отдельного указания оператора.
```

## Запреты для ИИ

- Не менять утверждённую схему во время её исполнения.
- Не добавлять команды вне утверждённых шаблонов.
- Не выдавать текстовый отчёт за доказательство без артефакта или API-записи.
- Не запускать сетевое действие только потому, что оно есть в черновике.
- Не заменять понятную схему скрытой технической карточкой.
