# red_drakon

Независимый веб-редактор DRAKON для регламента внутренней разведки. Он не
зависит от кода и базы `ops-panel` и не выполняет команды из схем. В режиме
наблюдения он только читает через API безопасную проекцию журнала запуска.

## Состав

- `public/` — простой редактор DrakonWidget и полный веб-интерфейс
  DrakonTech в `public/tech/`.
- `seed/` — исходные схемы регламента.
- `server.js` — локальная HTTP-служба, слушающая только `127.0.0.1:13339`.
- `drakon-web.service`, `drakon-web.nginx.conf` — служба и HTTPS-маршруты
  Nginx `/drakon/` и `/drakon-tech/`.
- `seed-tech-project.js` — однократный импорт схем в проект `reglament`.
- `workflows/08-no-creds-siluet.drakon` — единственная утверждаемая схема 08:
  текст блока одинаков для оператора и агента, а переходы задают алгоритм.
- `workflows/09-no-creds-full-siluet.drakon` — полный проект этапа без
  учётных данных, разбитый на силуэты и связанный с техниками MITRE. Он пока
  не имеет исполнителя и не запускается на сети.
- `worker/workflow_runner.py` — строго ограниченный исполнитель схемы 08 с
  сухим прогоном и
  хеш-цепочкой журнала.

## Данные и безопасность

Рабочие состояния хранятся отдельно от исходников: `state.json` для простого
редактора и `tech-state.json` для веб-интерфейса Desktop. Сервис не открывает
внешний порт: внешний доступ возможен только через Nginx с авторизацией.

Пока нет блокировки одновременной правки, разграничения ролей и журнала
версий. Не использовать для параллельного редактирования до добавления этих
механизмов.

## Единая схема 08

Схема `08-no-creds-siluet` открывается в DRAKON Tech. Текст каждого блока —
единое описание для оператора и воркёра; отдельной карточки агента нет.
Сама схема определяет допустимую последовательность блоков. Исполнитель
сверяет тексты и номера блоков с утверждённой схемой и содержит закрытый список
разрешённых действий; это защита от произвольной команды, а не второе описание
алгоритма. Агент получает только режим запуска исполнителя и не выбирает
следующий шаг самостоятельно.

В режиме наблюдения DRAKON Tech получает из панели безопасную проекцию
хешированного журнала и временно подсвечивает шаги выбранного IP VPN-цели.
Серый означает, что блок ещё не выполнялся; синий — выполняется; голубой —
контрольная точка; зелёный — успешно завершён; жёлтый — остановлен; красный —
ошибка. Цвета никогда не записываются в `.drakon` и Git. Для чтения журналов задать
в `/etc/drakon-web.env` права `0600`: `OPS_PANEL_URL=https://...` и отдельный
`DRAKON_VIEW_TOKEN` владельца или администратора с правом только чтения.
Утверждение схемы — ручной Git-коммит и тег
`workflow/08-no-creds-siluet/vN`. Воркера запускают только с SHA такого коммита: исполнитель дополнительно требует
тег, указывающий ровно на этот SHA. До `--execute` он не выполняет сетевых
действий, а после VPN всегда останавливается перед discovery. Второй запуск
возможен лишь с тем же журналом и явным `--approve-discovery`; только тогда
разрешён `nmap -sn` по маршрутам `ppp0` не крупнее `/16`.

Для каждого блока исполнитель сначала записывает событие «начат», затем
«завершён» или «ошибка» в локальный журнал с хеш-цепочкой. Безопасная копия
события передаётся в панель. При недоступности панели она остаётся в локальной
очереди и передаётся позднее; сетевые действия при этом не повторяются.

## Правило силуэта

Большую схему строят не как бесконечную цепочку или паутину переходов, а как
силуэт: последовательность логически законченных частей алгоритма. Это правило
обязательно для всех новых и изменяемых схем регламента.

- Один силуэт описывает один законченный этап и имеет понятный результат.
- Штатный, ожидаемый путь идёт сверху вниз по левой вертикали — «шампуру».
- Развилки ведут только вправо. Отклонения, остановки и ошибки располагаются
  правее штатного пути; чем правее ветвь, тем менее штатна ситуация.
- Внутри блока — одна однозначная мысль и действие. Текст блока одинаково
  обязателен для оператора, агента и исполнителя.
- У силуэта нет пересечений линий. Связанные действия разных ветвей, которые
  должны произойти одновременно по смыслу, располагают на одной горизонтали.
- Если часть перестаёт читаться целиком на одном экране, её выделяют в
  следующий силуэт с явным входом и результатом, а не уменьшают шрифт и не
  добавляют дальние переходы.

Для схемы 08 силуэты идут в таком порядке: «граница и VPN», «проверка
маршрутов», «контрольная точка», «обнаружение живых хостов», «загрузка
результатов и завершение». Все результаты и переходы этих частей остаются в
единственном файле `.drakon`, который исполняет воркёр.

Схема 09 развивает этот опыт до полного этапа: «граница и режим», «живые
хосты», «поверхность сервисов», «безучётная проверка», «доказательства и
охват», «завершение». Каждое расширение её исполнителя вводится отдельным
экспериментом после ручной проверки и утверждения новой версии схемы.

```bash
worker/run-workflow.sh --task-id 123 --schema-ref <утверждённый-SHA> --dry-run checkpoint
```

После успешной контрольной точки оператор отдельно разрешает продолжение:

```bash
worker/run-workflow.sh --task-id 123 --schema-ref <утверждённый-SHA> \
  --resume ~/.local/state/red_drakon/runs/<журнал>.json --approve-discovery
```

## Установка

На целевой машине развернуть этот репозиторий в `/root/drakon-web`, установить
файлы службы и Nginx, проверить `nginx -t`, затем запустить
`drakon-web.service`. Пароль HTTP-авторизации хранить вне Git с правами `0600`.
